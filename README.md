# Практическая работа 2

Продолжение проекта учета поступлений в морг. Основа — последняя версия первой работы, коммит `7058d3c`.

## Что добавлено

- `Model`: `Record` и интерфейс `IDomainObject` со свойством `ID`.
- `DataAccessLayer`: интерфейс `IRepository<T>` и операции `Add`, `Delete`, `ReadAll`, `ReadById`, `Update`.
- `DBContext` и `EntityRepository<T>`: работа с SQLite через Entity Framework 6.
- `DapperRepository<T>`: те же операции через SQL-запросы Dapper.
- `BusinessLogic`: существующий `Logic`, который теперь обращается к репозиторию вместо списка в памяти.

`Logic` вынесен из `Model`, чтобы модель не зависела от слоя данных. Пространство имен `Model` оставлено прежним: исходники форм и консоли не пришлось менять. В проектах представления добавлена ссылка на `BusinessLogic`.

У `Record` сохранено публичное автосвойство `Id`, которое уже используется формой и консолью. Свойство `ID` интерфейса явно обращается к тому же `Id`. Это один идентификатор, а не два разных значения.

## Запуск

Нужны Visual Studio 2022 с разработкой классических приложений .NET и .NET 8. Отдельный сервер базы данных устанавливать не нужно: SQLite подключена пакетами NuGet.

Открыть `lab1.sln`, восстановить пакеты NuGet и выбрать запускаемый проект: `lab1` для WinForms или `ConsoleApp` для консоли.

Пакеты в `DataAccessLayer`: `EntityFramework` 6.5.2, `Dapper` 2.1.89, `System.Data.SQLite` 2.0.4, `System.Data.SQLite.EF6` 2.0.3 и `SQLite` 3.54.0. Их видно в VS через «Управление пакетами NuGet». `DBConfig` регистрирует провайдер SQLite для EF6; пакет `SQLite` содержит сам движок базы данных.

При первом обращении создается файл `%LOCALAPPDATA%\lab1\lab1.db` и таблица `Records`. Консоль и WinForms используют одну базу, записи сохраняются после закрытия программы. Создание таблицы для обоих сценариев выполняется через `DBContext`; CRUD в `DapperRepository<T>` выполняется SQL-запросами Dapper. Значения передаются параметрами, а не добавляются в SQL конкатенацией.

По умолчанию выбран EF. Для проверки Dapper запустить приложение из PowerShell в папке решения:

```powershell
$env:LAB1_REPOSITORY = 'Dapper'
dotnet run --project ConsoleApp
```

Для формы заменить последнюю строку на `dotnet run --project lab1`. Для возврата к EF установить `$env:LAB1_REPOSITORY = 'EF'`. Переменная действует в текущем PowerShell и запущенных из него приложениях; на уже открытый VS она не влияет. При необходимости можно заменить создание репозитория в конструкторе `Logic` и пересобрать решение.

Для другого файла базы задать переменную `LAB1_DATABASE` со строкой подключения SQLite, например `Data Source=C:\путь\проверка.db`. Папка выбранного файла должна существовать. Если переменная отсутствует, используется общий файл в `%LOCALAPPDATA%\lab1`. Для добавления другой сущности нужно описать ее таблицу и включить ее в `DBContext`; Dapper использует имя таблицы из имени типа с окончанием `s`, ключ `Id` или `ID` и остальные публичные свойства как столбцы.

## Что проверить

1. Добавить запись, закрыть и снова открыть приложение. Нажать «Показать все» в WinForms: форма и обработчики остались прежними, автоматическая загрузка таблицы при открытии не добавлялась.
2. Создать запись через EF, прочитать и изменить через Dapper. После перезапуска EF проверить изменения.
3. Проверить чтение по id, изменение без изменения значений, удаление и отсутствующий id.
4. Проверить занятую камеру и номера камер 0, 1, 10, 11.
5. Проверить поиск по части причины без учета регистра и списки занятых и свободных камер.
